# 11. Interview Preparation: 10 Questions, 10 Answers

> Covers brief section 46. Practise saying these answers out loud, in your own words. Interviewers look for understanding, not memorisation.

---

### 1. Explain your project.
I built a Social Media Privacy Risk Assessment Framework. It's a defensive tool where users answer 53 questions about their *own* social-media settings, like whether their phone number is public, whether MFA is on, or whether they post travel plans in advance. The engine turns each answer into a risk value between 0 and 1, scores ten categories such as location, account security and digital footprint, and combines them with configurable weights into a 0–100 score with four levels. It then ranks the findings, gives prioritised recommendations, and has a simulator that shows how much the score drops if you fix specific things. For my fictional demo profile, eleven changes took it from 82, Critical, to 53, High. It's Flask with SQLite and Chart.js, has 65 automated tests, and the main design constraint was that it never collects personal data. It asks *whether* your phone is public, never *what* it is.

### 2. What's the difference between privacy and security, and how does your project show it?
Security is about who can get into the account; privacy is about what's exposed and to whom. You can have a strong password and MFA and still show your full birthday, workplace and live location to everyone. My framework keeps Account Security as its own category next to nine exposure categories, so the results make that gap visible. I also show "security controls on: x of 10" separately from the overall score. A fully private profile with a reused password still gets an Immediate recommendation.

### 3. What is a digital footprint, and how did you assess it without tracking anyone?
The active footprint is what you post deliberately; the passive one is data generated through your activity. I deliberately didn't measure anyone's actual footprint, because that would mean searching for real people. Instead Category J asks about *practices*: do you review old posts, do you have old accounts still active, when did you last review your settings, do you use the same username everywhere, have you searched yourself. Those habits are what actually control how the footprint grows.

### 4. How does oversharing increase social-engineering risk?
Social engineering works by building trust or urgency. If a scammer knows your employer, your college or that you're travelling, a fake message that mentions those true details feels legitimate. So public context is raw material for a pretext. On the defensive side I assess behaviours like checking links, never sharing OTP codes, and verifying urgent "friend" requests through another channel. I wrote awareness material on it, but I intentionally included no example scam messages, because the project is about recognising risk, not creating it.

### 5. How does your risk-scoring model work, and what are its weaknesses?
Each answer maps to a risk value through a scale. For example, "MFA enabled" is inverted, so No = 1.0, and "Not sure" is 0.7 because you can't rely on a control you can't confirm. Each question has a weight, and a category score is the weighted average times 100. The overall score is another weighted average, where Personal Information, Location and Account Security are 15% each. Then 0–20 is Low, up to 40 Moderate, up to 70 High, and above that Critical. I tested the boundaries at 20/21, 40/41 and 70/71. The weakness is that the weights are educational assumptions, not calibrated on incident data, and the model is linear, so it misses aggregation effects where two exposures together are worse than their sum. I say that clearly in the UI and docs. I chose a linear model because every point of the score can be explained to the user.

### 6. How did you apply data minimisation?
At three levels. At the input, questions ask only whether something is visible, and the validator is an allow-list: only known question IDs and fixed answer codes like YES or PUBLIC. So if someone sends a real phone number, the request is rejected with a 400. In processing, raw answers are scored and discarded; they stay in the browser's sessionStorage, not on the server. In storage, saving is off by default. If the user opts in, I store only the scores and finding types, and I have a test that checks the database schema against an allow-list of columns and dumps the whole database to prove no raw answers or plaintext tokens are in it.

### 7. Why is MFA so important, and does it fix privacy?
MFA means a stolen or reused password alone usually isn't enough to log in, which blocks credential stuffing and most phishing that only captures passwords. Phishing-resistant methods like security keys are strongest, so my recommendation says to use the strongest method the platform supports. But MFA does nothing about what your profile shows publicly, which is why it only affects the Account Security category. Also, MFA can be bypassed if someone tricks you into sharing the code. That's why "shared a verification code" is always an Immediate priority, just like MFA being off.

### 8. What's the risk with third-party applications?
When you connect a quiz, game or "sign in with" integration, it gets access to parts of your profile, and that access often continues long after you stop using it. That data then sits outside your privacy settings. I assess whether people review connected apps, whether unused apps are still connected, how often they use social login, and whether they grant permissions to quiz apps. The recommendation is based on the principle of least privilege: keep only the access you need, and revoke the rest regularly. In my synthetic data, connected-app review was the least-adopted control at about 22%.

### 9. How does the application itself follow Privacy by Design?
I mapped each principle to code. Data minimisation is the allow-list validation and a schema with no PII columns. Privacy by default means storage is off by default. Transparency comes from the overview page listing what's never collected and the consent text saying exactly what's stored and for how long. User control is a one-time deletion token (I store only its SHA-256 hash) and a DELETE endpoint. Retention limitation means results older than 30 days are purged. Secure processing covers CSP headers, output escaping, parameterised SQL and rate limiting. Least privilege shows up in the report having a CSP that allows no scripts, and a Permissions-Policy that blocks camera, microphone and geolocation. Most of these have a test proving them.

### 10. How did you test it?
I have 65 pytest tests in four groups. For the scoring tests, each one starts from a fully private profile that scores exactly 0 and changes a single answer, so I know exactly which input caused which finding. I also check calculations against hand-computed values: phone public alone should make Personal Information 100 × 3 / 14.5 = 21. There are boundary tests at every threshold. API tests cover saving and retrieving, reports, the simulator and the dashboard. Security tests check XSS escaping in reports, security headers, that rate limiting returns 429 on the fourth request with a limit of three, oversized requests, deletion with right and wrong tokens, and retention purging. I also tested manually in the browser in light and dark mode and at mobile width. Every test uses a temporary database, so the tests are isolated and repeatable.
